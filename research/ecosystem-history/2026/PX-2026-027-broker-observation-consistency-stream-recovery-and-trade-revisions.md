# PX-2026-027 — Broker observation consistency, stream gaps and trade-revision semantics

**Research date:** 2026-11-08  
**Status:** official-documentation review completed; delivery, snapshot and correction contracts remain unproven  
**AlgoX area:** broker adapter / order-state observations / event recovery / execution ledger  
**Providers:** Zerodha Kite Connect, Upstox Developer API, DhanHQ API v2  
**Inputs:** PX-2026-024, PX-2026-025 and PX-2026-026  
**Mode:** research and requirements refinement only  
**Non-goals:** no broker account access, API calls, sandbox/production interaction, real order, code implementation, paid service, PR or merge to `main`

## Executive finding

The public provider documentation describes useful live order-update streams and REST order/trade read APIs. It does not establish a shared contract for:
- durable stream sequence numbers or resume cursors;
- replay of all events missed during a disconnection;
- exactly-once or at-least-once delivery;
- atomic snapshots across order and trade endpoints;
- read-after-write visibility guarantees for every reconciliation query;
- the lifecycle and identity of trade corrections, busts or reversals.

The message fields are useful for identification and observation, but must not be overinterpreted:
- Kite WebSocket order messages carry the postback payload; HTTP postbacks include a checksum. The reviewed payload does not define an event-sequence cursor.
- Upstox portfolio updates include order IDs, timestamps, `order_request_id` and `order_ref_id`. The documentation describes `order_request_id` as a count of requests sent and `order_ref_id` as an internal order identifier, not a stream event sequence.
- Dhan live updates include order number, exchange order number and timestamps such as `LastUpdatedTime`; the reviewed message schema does not define a sequence/cursor field.

**Recovery conclusion:** reconnecting a socket restores a live observation channel; it does not, by itself, close the event-history gap. AlgoX must retain a disconnect interval, reconcile current orders and individual trades through REST, and separately record whether event-history completeness remains unknown. REST reads from separate endpoints must not be treated as one atomic snapshot unless the provider documents that guarantee.

The reviewed trade endpoints expose execution identifiers and quantities. They do not describe a consistent trade-bust/correction protocol. Raw execution records must remain immutable, and any future correction model needs provider-specific authoritative evidence.

## 1. Scope and evidence method

This audit reviews public official documentation for:
- Kite order history, order book, trades, WebSocket order postbacks and HTTP postbacks;
- Upstox portfolio stream, streamer reconnect methods, order history/book and trade endpoints;
- Dhan Live Order Update, day order book, tradebook and trades by order.

Evidence labels:
- **SOURCE-DOCUMENTED:** directly described by the relevant official API page.
- **NOT DOCUMENTED IN REVIEWED PAGE:** the reviewed page does not provide the claimed contract. This does not prove that provider internals cannot have the capability.
- **DERIVED REQUIREMENT:** a conservative AlgoX obligation.
- **UNKNOWN:** no authoritative guarantee has been established.

No live stream was connected, no endpoint was called, no credentials were used and no provider behaviour was probed.

## 2. Zerodha Kite Connect

### 2.1 REST order and trade observations

The Kite Orders page documents:
- `GET /orders` for all open and executed orders for the day;
- `GET /orders/{order_id}` for the history of a given order;
- `GET /trades` for all executed trades for the day;
- `GET /orders/{order_id}/trades` for trades generated by an order.

Order response attributes include `order_timestamp`, `exchange_timestamp`, `exchange_update_timestamp`, `filled_quantity`, `pending_quantity` and `cancelled_quantity`. Trade records include exchange-generated `trade_id`, `fill_timestamp`, `order_id` and exchange identifiers.

These are distinct REST resources. The reviewed page does not state that the orders response and trades response are one atomic, same-watermark snapshot, nor does it specify read-after-write consistency bounds for a recently accepted order or execution.

### 2.2 WebSocket and postback observations

The WebSocket documentation says text-mode messages include an `order` type whose `data` contains the full order postback payload. The separate HTTP postback documentation defines a SHA-256 checksum over order identity, timestamp and API secret; this allows the receiver to verify message authenticity.

Authentication/integrity is not the same as delivery completeness. The reviewed WebSocket/postback pages do not define:
- a monotonically increasing event sequence for order messages;
- a cursor from which missed updates can be resumed;
- a replay window or replay API for a disconnected interval;
- exactly-once or at-least-once event delivery;
- an atomic relation between a postback and the REST order/trade snapshots.

The checksum protects the integrity/authenticity of a received HTTP postback; it does not prove that no postback was missed or that multiple updates arrived in exchange order.

Sources:
- https://kite.trade/docs/connect/v3/orders/
- https://kite.trade/docs/connect/v3/websocket/
- https://kite.trade/docs/connect/v3/postbacks/

## 3. Upstox

### 3.1 Portfolio Stream Feed

The official Portfolio Stream Feed page states that order updates are communicated over WebSocket when connected and begin immediately after successful connection. It also states that account order updates are sent regardless of which Upstox platform originated the order.

The sample order message contains fields including:
- `order_id`, `exchange_order_id`, `tag`;
- `order_timestamp` and `exchange_timestamp`;
- `filled_quantity`, `pending_quantity` and `status`;
- `order_request_id`, described as the count of requests sent apart from the first;
- `order_ref_id`, described as an identifier for the order for internal usage.

These fields assist order/request attribution. The documentation does not describe either `order_request_id` or `order_ref_id` as a stream sequence number, event ID, resume cursor or replay offset.

The Upstox Streamer Functions documentation includes `auto_reconnect(enable, interval, retryCount)`, which configures reconnect interval and maximum retries. This is a reconnect-control feature; the reviewed page does not say that events missed before reconnection are replayed or that a replay cursor is resumed.

The portfolio feed docs do not define a common durable event sequence or delivery guarantee for the order update stream.

### 3.2 REST order and trade observations

Upstox documents:
- current-day order book;
- order history by `order_id` or `tag`;
- current order details;
- daily trades, trades by order and trade history.

The order book and order-history pages say records remain available for one trading day and are automatically removed at session end. Trade endpoints are separate reads from order state. The reviewed pages do not establish that a set of order and trade queries forms an atomic snapshot or that every newly generated event is immediately visible to every endpoint.

**Important interpretation:** `order_request_id` is request-count metadata and `order_ref_id` is an internal order identifier. They must not be treated as an event-stream sequence or a replay cursor without an explicit provider contract.

## 4. DhanHQ

### 4.1 Live Order Update

Dhan says its WebSocket can deliver real-time updates for all orders in the account, irrespective of the platform used to place them.

The sample `order_alert` message includes:
- `OrderNo` and `ExchOrderNo`;
- `OrderDateTime`, `ExchOrderTime` and `LastUpdatedTime`;
- `RemainingQuantity`, `TradedQty`, `AvgTradedPrice`;
- `Status`, `LegNo`, `CorrelationId` and remarks.

These fields identify the order and describe its last updated state. The reviewed schema does not define an event sequence number or stream resume cursor. `OrderNo` is an order identifier and `LastUpdatedTime` is a timestamp; neither is documented as a monotonically increasing event offset.

The reviewed Live Order Update page does not specify a replay period, a replay request, or exactly-once/at-least-once delivery semantics.

### 4.2 REST order and trade observations

Dhan documents separate:
- `GET /orders` for the orders requested during the day;
- `GET /orders/{order-id}` and `GET /orders/external/{correlation-id}`;
- `GET /trades` for the day tradebook;
- `GET /trades/{order-id}` for trades belonging to one order.

Order observations have fields including `createTime`, `updateTime`, `exchangeTime`, `remainingQuantity` and `filledQty`. Trade records include `exchangeTradeId`, `tradedQuantity`, `tradedPrice` and timestamps.

The page documents trade identities and read endpoints, but not an atomic cross-resource snapshot, read-after-write visibility bound, event replay cursor or trade-correction/bust semantics.

Sources:
- https://dhanhq.co/docs/v2/order-update/
- https://dhanhq.co/docs/v2/orders/

## 6. Important distinction: order request counters are not stream sequence numbers

Upstox's `order_request_id` is described as the count of requests sent apart from the first, and `order_ref_id` uniquely identifies an order for internal usage.

The documentation does not say that these fields:
- identify every emitted WebSocket message;
- increment for every exchange status transition or trade;
- provide contiguous numbering without gaps;
- can be used to detect all missed messages;
- can be sent back to resume a stream after disconnection.

Therefore the adapter may preserve these fields as provider metadata but MUST NOT use them as an event replay cursor or a substitute for a missing sequence guarantee.

Similarly, Dhan's order number identifies an order, and its last-updated timestamp indicates an update time. Neither establishes a sequence of all order events. Kite's order/exchange timestamps and checksum identify/secure a payload but do not prove complete ordered delivery.

## 7. REST reconciliation is a point-in-time observation, not a historical event replay

The providers expose useful read paths, but order and trade state are retrieved through separate endpoints. Unless a provider explicitly documents atomic snapshot or a common watermark, the following can happen without either response being malformed:
- an order has been updated after the order-book query but before the tradebook query;
- a fill is visible in one endpoint before all associated order quantities/statuses have converged in another;
- the stream delivers an update while REST responses represent earlier or later observations;
- an old response arrives after a newer stream or REST observation.

A future reconciler must preserve query/capture times and raw responses and compare observations without pretending they share an atomic cutoff.

A single discrepancy should not cause an invented correction or forced quantity balancing. Reconciliation should repeat bounded reads according to provider limits; if the observations do not converge or no consistency guarantee exists, the derived state remains UNKNOWN or CONFLICT.

Even if the current order and trade totals ultimately agree, that does not reconstruct every missed intermediate status transition or prove the completeness/order of the event history.

## 8. Trade correction, bust and reversal semantics

The reviewed trade endpoints expose provider/exchange trade identifiers, prices, quantities and timestamps:
- Kite exposes an exchange-generated trade ID and fill timestamp.
- Upstox exposes trade IDs and order links through daily/per-order trade endpoints.
- Dhan exposes `exchangeTradeId` and trade quantities/prices by order.

The reviewed API pages do not specify a common contract for:
- trade busts or cancellation of an already-reported execution;
- corrected/replaced trade IDs;
- negative/reversal trade records;
- exchange trade cancellation notifications;
- how corrected trade values affect positions, P&L and contract-note reconciliation;
- retention and audit links from a correction to the original trade.

This is a **documentation gap**, not proof that corrections never occur or are not exposed through other broker statements/reports.

A future domain model must not mutate/delete the first observed raw trade when a later correction is reported. It should retain the original record and append the correction/reversal evidence with explicit linkage and provider semantics. If no authoritative correction linkage is available, the original and contradictory observations remain visible and the affected execution ledger stays unresolved.

## 9. Requirements refinements to PX-025

The existing PX-025 rules R-015 (stream reconnect), R-016 (immutable observations), R-017 (arrival order), R-018 (conflicting evidence) and R-030 (reproducible derivation) remain valid. This audit makes their requirements more explicit.

### R-034 — Stream-gap completeness requires a documented continuity contract

A stream reconnect MUST NOT be treated as proof that missed messages were replayed. Unless the provider documents a sequence/cursor plus replay/resume semantics and the adapter has verified that contract, the affected time interval MUST retain an explicit event-history completeness UNKNOWN state after reconnect, even if current order/trade state can later be reconciled.

### R-035 — Separate REST reads are not an atomic snapshot by default

Unless a provider documents a shared atomic snapshot/watermark or read-after-write guarantee, order and trade responses fetched separately MUST be retained as independently timed observations. The reconciler MUST NOT assume that two endpoint responses represent the same state cutoff or resolve temporary quantity/status differences by silently overwriting one observation.

### R-036 — Trade corrections are append-only and provider-defined

A future adapter MUST preserve original trade observations and any later correction, bust or reversal as separate linked evidence. It MUST apply economic reversal/replacement semantics only when the provider/exchange defines the correction identity and effect. Missing correction documentation MUST remain UNKNOWN; it MUST NOT be interpreted as proof that trade records are immutable forever.

## 10. Design implications

1. **Two independent recovery results:** distinguish current order/trade state reconciliation from historical stream completeness. The first can sometimes be established even while the second remains UNKNOWN.
2. **Observation provenance:** store query start/end times, local receive time, provider timestamps, endpoint/stream source, raw payload reference/hash and parser version.
3. **No fabricated event order:** event timestamps and order IDs are not automatically event-sequence IDs. Preserve ambiguity where no causal ordering contract exists.
4. **Reconnect protocol:** record disconnect interval, reconnect the stream, durably buffer new updates, query current order book and trades, then re-read unresolved orders/trades. Never label the historical gap replayed without evidence.
5. **Correction-safe trade ledger:** immutable raw trade events plus linked correction events; economic netting only after provider-specific correction semantics are known.
6. **Session-end handling:** because provider order views are day-scoped, persist end-of-session evidence and unresolved gaps locally before provider history expires.
7. **No provider probing by default:** the open questions may be closed by official docs or an authorized provider clarification. This record does not authorize actual account/sandbox API experiments.

## 11. Remaining provider questions

- Does each provider publish any non-public or separate subscription interface for replaying order events after a disconnect?
- Are orderbook/tradebook REST reads strongly consistent, eventually consistent, or served from different processing systems?
- Is there a provider-defined snapshot cutoff for order and trade data?
- Can trade IDs be amended, replaced, cancelled or busted after initial reporting, and how are those links represented?
- Are postbacks/WebSocket messages retried on receiver failure, and under what acknowledgement policy?
- Are there provider event IDs in SDK models or supplementary documents not shown in the public pages reviewed?
- What exact local/session retention applies to raw order/trade endpoints after the trading session ends?

Until there is authoritative evidence, each remains UNKNOWN.

## 12. Research decisions and non-authorization

- **ACCEPT:** live update streams are low-latency observation channels, not assumed complete event logs.
- **ACCEPT:** reconnect and read-side reconciliation are separate steps; neither proves historical event replay.
- **ACCEPT:** separate order and trade REST responses are independently timed unless provider atomicity is documented.
- **ACCEPT:** preserve Upstox request/order metadata without treating it as a stream cursor.
- **ACCEPT:** trade correction/bust handling must preserve originals and use provider-specific correction links.
- **DEFER:** declaring any of the three providers' streams gap-free, exactly-once, replayable or globally ordered.
- **DEFER:** trade-bust/correction implementation until provider contracts and example payloads are available.
- **NOT AUTHORIZED:** broker connections, sandbox/production calls, real orders, code changes, paid services, credentials/IP changes, PR creation or merge to `main`.

**Final status:** PX-027 provider observation consistency and stream recovery audit documented. PX-025 has been refined with R-034 to R-036 and AT-044 to AT-049. No broker API or test environment was used.
