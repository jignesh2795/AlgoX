# Decision Framework

## Decisions

### ADOPT
Use an existing component or approach directly when requirements, evidence, license, security, and operational constraints permit.

### ADAPT
Modify an existing approach when adaptation provides a better fit and reuse is legally and technically appropriate.

### WRAP
Isolate an external component behind an internal contract when replacement, compatibility, or dependency risk matters.

### BUILD
Create a capability when adequate solutions do not exist or strategic requirements justify ownership.

### REJECT
Do not use an approach when evidence, requirements, risk, cost, licensing, maintenance, or complexity make it unsuitable.

## Required decision inputs

- Problem and requirements
- Alternatives considered
- Evidence and source provenance
- Experiments/benchmarks
- Technical trade-offs
- Cost and operational burden
- Security and regulatory implications
- License compatibility
- Confidence and unresolved uncertainty

## Principle

Do not select an architecture because it is popular. Select it because evidence shows that it satisfies the target requirements with acceptable trade-offs.
